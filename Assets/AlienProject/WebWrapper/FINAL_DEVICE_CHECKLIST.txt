2. FIREBASE И ПЕРЕХОД В ИГРУ
Узел: https://been-there-atlas-default-rtdb.firebaseio.com/apps/sunny_joy/webview.json
Текущее значение: {"enabled":true,"url":"https://application-test-qa.top/test_page/"}
[ ] enabled=true + правильный HTTPS URL: открывается эта страница.
[ ] В Firebase Console временно поставить enabled=false и перезапустить: открывается игра.
[ ] Восстановить enabled=true; следующий полный запуск снова открывает WebView.
[ ] Запуск без сети: открывается игра, без синего экрана ошибки и бесконечной загрузки.
[ ] Вернуть сеть и полностью перезапустить: снова попытка чтения Firebase.
[ ] На отдельном узле проверить пустой/неверный ответ, отказ чтения и недоступную страницу:
    ожидается переход в игру. Не ломать общий узел, если его используют другие устройства.
[ ] Изменение URL вступает в силу при следующем запуске без очистки данных приложения.
[ ] В игре проверить профиль/сохранение, раунд, жизни, паузу, повтор, звуки, скины.
[ ] Проверить опубликованные правила БД: чтение нужного узла доступно, публичная запись закрыта.

  Сейчас: только GET Firebase; ссылка не зависит от organic/non-organic, SDK запускаются отдельно.
- Notion: закреплённый маршрут в рамках установки, сохранённый URL и offline-заглушка.
  Сейчас: новое чтение на каждом запуске; ошибка/отсутствие сети -> игра на этот запуск.
- Notion: PushPanel перед WebView. Сейчас: только игровой маршрут, WebView без PushPanel.
- Notion: обновление push-токена и PUT interaction.php?message_id=... с af_id при клике.
  Сейчас: PHP не вызывается; для этой аналитики и рассылки нужен отдельно подключённый бэкенд.
Ответ PHP 404 с {ok:false,message:"No data"} в документации является штатным отрицательным
решением (например, для неподходящей атрибуции), а не сам по себе доказательством поломки сервера.
